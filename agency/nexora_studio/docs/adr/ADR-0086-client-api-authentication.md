# ADR-0086: Client API + Authentication

Date: 2026-09-07
Phase: 47.35
Status: Accepted

## Context

Phase 47.31 established the FastAPI BFF as the ONE canonical headless API
boundary. Phase 47.33 established `ClientEnvironmentService` as the client
Odoo database lifecycle owner. Phase 47.34 established deterministic,
allowlisted module provisioning, and Phase 47.34.x hardened agency/client
database identity checks.

Phase 47.35 adds the smallest authenticated client-facing API surface needed
before frontend binding:

```
Client Principal
    → authentication
    → authorized ClientEnvironment
    → Phase 47.34.x agency DB safety guard
    → isolated Client Odoo DB
    → explicit capability/business operation
```

## Decision

### 1. Client API boundary

Client routes live inside the existing FastAPI application and canonical BFF,
under `/api/v1/client/*`. No second FastAPI application, gateway, router
stack, or authentication boundary was created. Existing Console routes and
JWT behavior remain unchanged.

Implemented routes:

| Route | Capability | Operation |
|---|---|---|
| `GET /api/v1/client/whoami` | none | authenticated client identity + server-derived capabilities |
| `GET /api/v1/client/health` | none | environment/backend health |
| `GET /api/v1/client/products` | `products` | explicit product read |
| `POST /api/v1/client/leads` | `leads` | explicit lead creation |

No raw Odoo model, method, SQL, Python expression, or arbitrary RPC endpoint
exists.

### 2. Authentication model

Client authentication uses a per-ClientEnvironment bearer token with the
platform-owned prefix `nex_cli_`.

- A cryptographically random plaintext token is generated by the existing
  `ClientEnvironmentService`.
- Only the SHA-256 hash is stored on `nexora.client_environment`.
- Plaintext is returned once by the control-plane issuance action.
- Tokens expire and can be revoked or rotated.
- Rotation invalidates the prior token immediately.
- Client tokens are not connector credentials and do not reuse
  `OdooSecretsProvider` as a token store.

The existing Console JWT remains a separate credential class. A Console JWT
cannot authenticate `/api/v1/client/*`; a client token cannot authenticate
Console `/api/v1/*` routes.

### 3. Authorization model

Authentication and authorization are separate:

```
Bearer client token
    → exactly one ClientEnvironment
    → environment state validation
    → server-derived approved capabilities
    → verified installed module
    → explicit operation
```

The client request supplies no project ID, environment ID, client ID, or
database name. The token is the only tenant selector. This removes the IDOR
class rather than trying to secure arbitrary IDs after parsing them.

### 4. Client identity and environment resolution

`nexora.client_environment_service._resolve_client_token` hashes and looks
up the token, checks active state and expiry, and returns the one associated
environment. `client_api_*` methods then validate `deleted`/`ready` state.

Identity is server-derived from the token's stored environment and project
relationship. No client-supplied environment selector is accepted.

### 5. Database resolution and agency protection

The service reads the stored `ClientEnvironment.db_name`, then reuses the
canonical Phase 47.34.x `_is_agency_database` guard before client operations.
The guard remains fail-closed. The agency database can never be selected by
client API activity, even if a legacy/corrupted environment record points at
it.

Client Odoo access uses the existing proven in-process Odoo mechanism:

```
Registry(client_db_name)
    → context-managed cursor
    → SUPERUSER Environment
    → explicit product/lead operation
```

No second connection pool or database-selection mechanism was introduced.

### 6. Capability authorization

Capabilities are derived from the persisted, approved Phase 47.34 Module Plan
and filtered through the platform-owned `CAPABILITY_MODULE_ALLOWLIST`. The
client cannot claim capabilities in a request.

For capability operations, the service also verifies the corresponding
approved technical module is actually installed in the client DB. The public
API exposes business capabilities (`products`, `leads`), never technical
module identifiers.

`nexora.capability_registry` remains untouched; it is the MCP/tool registry,
not the project capability domain.

### 7. Odoo access and BFF ownership

The BFF delegates through the existing `OdooClient` JSON-RPC adapter, the
same adapter pattern used by existing `builder_assistant_service`, execution,
project, and session adapters. The BFF is a thin transport/authentication
adapter; client business/database logic remains in the canonical Odoo
service owner.

### 8. Error semantics

The Odoo service returns stable sanitized error codes, mapped by the BFF:

| Code | HTTP |
|---|---:|
| `CLIENT_AUTH_INVALID` | 401 |
| `CLIENT_AUTH_EXPIRED` | 401 |
| `CLIENT_ENV_DELETED` | 410 |
| `CLIENT_ENV_NOT_READY` | 503 |
| `CLIENT_CAPABILITY_UNAVAILABLE` | 403 |
| `CLIENT_DB_UNAVAILABLE` | 503 |
| `CLIENT_REQUEST_INVALID` | 422 |
| `CLIENT_BACKEND_ERROR` | 502 |

Unexpected transport errors are sanitized by client routes. No database
names, credentials, paths, stack traces, or raw Odoo exceptions are returned.

### 9. CORS and browser security

The existing explicit `settings.CORS_ORIGINS` allowlist remains unchanged.
`allow_credentials=True` is retained only with explicit origins; wildcard
credential CORS was not introduced. No new middleware or rate-limit service
was created. Rate limiting remains a documented future operational concern.

### 10. Audit logging

Existing Python logging is reused for sanitized events:

- `client.auth_failed`
- `client.authenticated`
- `client.authz_denied`
- client operation failure/success identifiers without tokens

Tokens and credential values are never logged. No telemetry subsystem was
created.

### 11. Generation relationship

No generation component changed. The existing chain remains:

```
BuilderSessionService
    → GenerationCoordinator
    → GenerationRuntime
    → WebsiteGenerationPipeline
```

Client API/authentication is a sibling control-plane/backend workflow, not a
generation responsibility.

### 12. Module provisioning relationship

Client API/authentication does not install modules and accepts no module
identifiers. Module provisioning remains:

```
Capability → module policy → Module Plan → ClientEnvironmentService → Odoo modules
```

Client API operations consume the already-provisioned, verified result.

### 13. Explicit non-goals

- frontend binding (Phase 47.36)
- generated frontend changes
- client user/password/OIDC login
- refresh-token infrastructure
- arbitrary Odoo RPC/model exposure
- client API gateway
- new secret store
- connector/provider changes
- Console JWT changes
- generation pipeline changes
- rate-limiting infrastructure
- Graphify changes

## Consequences

- Client identity is established before DB resolution.
- Client requests cannot select arbitrary databases.
- Agency/client tenant isolation is enforced structurally and by the
  canonical database safety guard.
- The API is intentionally small and business-capability oriented.
- A client token is issued by the control plane and must be delivered to the
  client consumer through an operator-controlled process.
- Client operations are real and verified against the isolated client DB.

## Future

Phase 47.36 may bind the generated frontend to these explicit client routes.
Any future client-user authentication must remain distinct from connector
credentials and must preserve the token/environment/database separation
defined here.

## Addendum — Phase 47.35.x Red-Team Remediation (2026-09-08)

### 14. WebSocket boundary (F1)

`/ws/events` is an **agency-only** channel. Its sole consumers are the
agency Console frontend components (dashboard/workspace live panels); no
client application consumes it.

Authentication requirement (fail closed):

```
connect
    -> in-band first message {"type": "AUTH", "token": <Console JWT>}
    -> canonical security.auth.decode_token (the ONE validator)
    -> registered for broadcasts ONLY after a valid Console JWT
    -> otherwise closed 4401 with NO event payload ever sent
```

Rationale: browsers cannot attach an `Authorization` header to a
WebSocket handshake; the token transits the same-origin authenticated
first frame instead. No second JWT implementation, second validator, or
second credential class was introduced. Client API tokens (`nex_cli_*`)
are structurally not JWTs and are rejected by the canonical decoder —
client principals can never consume agency events. CORS is not treated
as an authorization boundary for WebSockets.

Authorization scope: all authenticated sockets are agency Console
principals; the existing event stream (SESSIONS_UPDATE / SYSTEM_HEALTH /
AI_OPS) is agency operational data and remains agency-only. Cross-tenant
client realtime is a future, separately-scoped concern.

### 15. Real transport verification (F2)

The Client API has been verified end-to-end through the REAL transport:

```
BFF client routes
    -> OdooClient (real adapter)
    -> HTTP JSON-RPC over :8069 (real Odoo server)
    -> nexora.client_environment_service
    -> real disposable Client DB (product read + lead create)
```

with a real disposable Odoo service account (created/deleted through the
registry for the run; credentials only transit process environment).
Failure semantics verified: invalid service credentials → sanitized 502;
Odoo unavailable → bounded timeout → sanitized 502. Agency DB
before/after module-state snapshot identical; no lead in the agency DB.

### 16. Superuser confinement invariant (F3)

Client Odoo `SUPERUSER` access is an **internal implementation detail**
behind the Nexora authorization/service boundary:

```
client authentication (nex_cli_ token)
    -> Nexora authorization (server-derived capabilities)
    -> explicit business operation only
    -> ClientEnvironment resolution (token-keyed, server-side)
    -> Phase 47.34.x agency DB safety guard (_is_agency_database)
    -> client DB only
    -> controlled Odoo superuser operation
```

The invariant: **Odoo SUPERUSER privileges are confined to the resolved
Client DB and are reachable only through explicitly allowlisted Nexora
client operations.** `Client → Odoo SUPERUSER` directly is forbidden and
impossible: the client credential never reaches Odoo, and the only
execution paths are the four allowlisted `client_api_*` operations with
field whitelists.

### 17. Future `client_api_*` invariant (hard rule)

Any future `client_api_*` operation MUST:

1. authenticate the principal (token → `_client_api_prelude`);
2. authorize the principal (server-derived capability, verified module);
3. derive the ClientEnvironment server-side (no request selector);
4. resolve the client DB through canonical ownership only;
5. pass the Phase 47.34.x agency DB safety guard;
6. execute only an explicit allowlisted business operation (fixed
   field/projection whitelist — never model/method/args passthrough);
7. sanitize the response (stable error codes, no internals).

Generic Odoo execution under the client API is architecturally forbidden.
The `test_phase47_35x_security_invariants` suite enforces: every
`client_api_*` method must call the shared prelude, the prelude order is
auth → env state → agency guard → capability, no generic RPC surface
exists, and superuser cursors are opened only for the resolved client DB.
