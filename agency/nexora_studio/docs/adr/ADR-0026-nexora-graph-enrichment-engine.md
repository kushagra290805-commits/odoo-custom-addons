# ADR-0026: Nexora Graph Enrichment Engine

## Status
Accepted

## Context
Phase 6B focuses on architectural governance and intelligence. While Graphify successfully extracts standard structural Python edges (AST and imports), it is fundamentally blind to dynamic relationships that form the core of the Nexora Studio framework:
1. **Odoo ORM relationships** (`self.env['nexora.ai_provider_manager']`)
2. **Odoo XML UI Bindings** (`<record model="ir.ui.view">`)
3. **FastAPI routing and dependencies**
4. **Semantic Pipeline Workflows** (AI Pipeline and Builder Pipeline relationships)

To achieve 100% architectural visibility and successfully answer dynamic dependency queries, we need to bridge this gap. However, patching or forking Graphify is not permitted, as it would break upgrade paths and violate separation of concerns.

## Decision
We will implement the **Nexora Graph Enrichment Engine** as a post-processing layer entirely contained within Nexora Studio (`services/graph_enrichment/`).

1. **Loader & Exporter**: The engine will read the raw `graph.json` generated by Graphify, and ultimately export an `enriched_graph.json`, `.dot`, and `.mmd` without modifying or overwriting the original graph file.
2. **Modular Enrichers**: Specific enrichment rules will be encapsulated in independent classes extending `BaseEnricher`. 
   - `OdooRegistryEnricher`: Maps Odoo model strings (e.g., `_name = 'model'`) to Python classes and links dynamic `env['model']` calls to those targets.
   - `XMLViewEnricher`: Parses views and links UI elements to their backend models.
   - `FastAPIEnricher`: Parses FastAPI endpoint definitions and maps API boundaries.
   - `AIPipelineEnricher` & `BuilderPipelineEnricher`: Identifies high-level semantic workflow edges for the respective pipelines.
3. **Additive-Only Modification**: Enrichers are only permitted to generate new nodes (e.g., XML elements, HTTP routes) and new INFERRED edges. They must never mutate or delete the original graph structure.
4. **Explicit Edge Typing**: Every inferred edge will carry an explicit `relation` type (e.g., `ORM_REFERENCE`, `XML_REFERENCE`, `HTTP_ROUTE`, `AI_PIPELINE`) to allow filtering in visualization and query tools.

## Consequences
- **Positive**: 100% visibility into dynamic Odoo and FastAPI dependencies. Queries like "Who calls ProviderManager?" will accurately return dynamic Odoo ORM callers.
- **Positive**: Complete decoupling from Graphify. We can upgrade Graphify without breaking our enrichment logic.
- **Negative**: Adds a secondary processing step after the main Graphify extraction. The `run_graphify.py` or equivalent pipeline script must be updated to trigger the enrichment engine.
