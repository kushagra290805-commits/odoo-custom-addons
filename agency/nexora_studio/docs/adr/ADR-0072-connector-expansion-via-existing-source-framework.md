# ADR-0072: Connector Expansion Via The Existing Source Framework — 3D Component Sources And GitHub Repository Intelligence

## Status: Proposed
## Date: 2026-08-25

## Context

Nexora Studio's next connector expansion adds two high-value capabilities: (1) high-value 3D website-generation component/source connectors, and (2) GitHub repository intelligence/tools.

Phase 45.1 architecture audit (`docs/reports/phase45_1_connector_expansion_architecture_audit.md`) verified against actual code that:

- Tool execution is authoritatively owned by the MCP connector platform (`ConnectorRuntime` → `ConnectorDispatcher` → `McpConnector/McpTransport/McpProvider`) behind the `UniversalCapabilityRouter`, using the ADR-0069 namespace contract `{connector_id}.{tool_name}` → `tools.call`.
- Source discovery is owned by the Component Source Framework (CSF): `nexora.source_registry` rows loaded by `ProviderManager.load_from_registry()` (`services\source_framework\provider_manager.py:18-30`), wrapped in `McpSourceAdapter`, normalized into the `ComponentPackage` domain model (`services\source_framework\domain_models.py:15-31`), federated/ranked by `SearchEngine` + `ComponentRankingPipeline`, and consumed by exactly one production entry point: `ComponentDiscoveryEngine` (`services\generation\engines\component_discovery_engine.py:26-53`).
- `github_mcp` is a fully working declarative connector (`data/connector_github_data.xml`) whose tools are already consumed declaratively by two CSF sources (`react_bits`, `shadcn`) via `config_json.capability_map`.
- 3D rendering governance already exists (ADR-0064: React Three Fiber canonical renderer; R3F/Spline validation providers implemented). What does not exist is 3D *source ingestion* and *code-gen emission*.
- The audit found one functional defect (F-01: `SearchEngine` filters providers by the CSF token `'SEARCH'` while `McpSourceAdapter.capabilities` returns discovered MCP tool names — so all seeded MCP-backed sources are silently filtered out of federated search) and four parallel adapter/provider frameworks, two of which register overlapping sources (shadcn, react_bits exist in BOTH CSF and the UCEL COMPONENT-provider framework).

This ADR defines how the expansion plugs into the existing architecture without creating any parallel platform.

## Decision

1. **CSF is the single source-discovery plane.** All new sources — 3D and GitHub-repo-intelligence alike — are registered as `nexora.source_registry` rows and surfaced exclusively through `ProviderManager`/`SearchEngine`. No second registry, no side-channel source catalogs, no controller-level bypasses.

2. **GitHub repository intelligence extends the existing `github_mcp` connector.** New repo-intelligence functionality is delivered by expanding the set of `github_mcp` tools consumed through the canonical routing contract (ADR-0069 shorthand `{connector_id}.{tool}`), configured declaratively in `config_json.capability_map` of one or more CSF source rows. Where an ORM-level service surface is genuinely needed, the `_McpModelProviderMixin` pattern (`models/mcp_model_providers.py`) is the only sanctioned shape.

3. **3D sources are ordinary CSF sources whose qualifying outputs are ComponentPackages.** 3D ingestion follows the canonical chain: discovery intent → candidate identification → source/artifact retrieval (e.g., `get_file_contents`) → normalization into `ComponentPackage` → provenance/dependency metadata → ADR-0064 renderer metadata (`three_d_scene`, `glb`/`gltf` format, renderer expectation) attached **only to artifacts that qualify** as generation-ready components (actual scene/component code or assets present — never bare repository metadata). Validation of 3D requirements (e.g., `three`/`@react-three/fiber` dependency presence) happens at normalization time; ranking/resolution reuse the existing pipeline. Rendering/code-gen emission remains governed by ADR-0064 and the DesignProvider stack; this ADR covers ingestion and delivery only.

3a. **GitHub repository-intelligence artifacts are `RepositoryArtifact`s, not ComponentPackages.** The canonical domain model `RepositoryArtifact` (`services/source_framework/domain_models.py:78-85`: artifact_id/path/content/type/metadata/provenance) already exists and is the correct representation for repository trees, files, commits, and repo-level query results. Repository-intelligence sources therefore declare the semantic capability `REPOSITORY_INTELLIGENCE` and expose adapter methods returning `List[RepositoryArtifact]`, executed through the same `_execute` router chain. Repository artifacts deliberately bypass `ComponentRankingPipeline`, whose contract is explicitly ComponentPackage-typed (`component_ranking_pipeline.py:31`); ordering is inherited from tool results and no second ranking engine is created. Forcing repository data into a component-shaped structure is rejected as type abuse.

4. **Capability reconciliation (fixes audit defect F-01).** `source_registry.capabilities` (CSV field, currently parsed by nothing) becomes the authoritative CSF-level capability declaration for every source, using **semantic tokens** — `SEARCH`, `FETCH`, `COMPONENT_SOURCE`, `REPOSITORY_INTELLIGENCE` — never concrete MCP tool names. `McpSourceAdapter.capabilities` returns the parsed declared tokens; discovered tool names remain an internal correctness guard inside `_execute` (via a dedicated private helper). `SearchEngine`'s filter therefore works unchanged, MCP-backed sources participate in federated search, and concrete tool execution still validates against the discovered-tools set.

5. **Non-MCP adapter resolution is DEFERRED, not implemented here.** `ProviderManager.load_from_registry()` keeps its current MCP-only behavior this phase. Its non-MCP limitation (stubbed else-branch, `provider_manager.py:28-30`) is recorded as a **future consolidation item**; no dynamic `adapter_class` importing is introduced now because neither GitHub repository intelligence nor 3D source ingestion requires it (both are MCP-backed via existing connectors). When deferred consolidation lands, resolution must be allowlist-restricted to the `services.source_framework.adapters` namespace.

6. **Centralization is preserved.** Discovery (`SearchEngine` federation), normalization (`ComponentPackage` + `config_json.normalization` maps), indexing (optional persistence via the existing but currently unwritten `nexora.component_index`; no new index models), ranking (`ComponentRankingPipeline` — single engine), and resolution (`UniversalCapabilityRouter`) each remain the one and only mechanism. Any per-domain scoring needs extend `QualityScorer`/pipeline profiles rather than new engines.

7. **Credential ownership is unchanged.** All secrets flow exclusively through `nexora.mcp_credential` + the fail-closed `OdooSecretsProvider` resolution inside `McpOnboardingService._build_mcp_configuration`. `config_json` carries configuration only (capability_map/payload_mapping/normalization) and must never carry secrets — matching the Phase 29 migration contract. Transport-level auth (query/header, session binding, request-context propagation) follows ADR-0066/0067/0071 as-is.

8. **Security boundaries.** Adapter-class resolution is allowlist-restricted (decision 5). Source-supplied payloads pass through the same policy/security/middleware chain as every other router caller. New external endpoints follow the connector egress rules established for github_mcp/tavily/firecrawl. No credential material may appear in logs (Phase 44.2 guarantees preserved).

9. **What is intentionally NOT being introduced:** a second DIP or CSF; a second provider registry; a separate component-ranking engine; a separate 3D component framework; a duplicate GitHub orchestration layer or second GitHub REST client for production paths; new Odoo models; migrations of UCEL COMPONENT providers onto CSF (or vice versa) — the CSF↔UCEL boundary is documented instead: **CSF owns generation-time source discovery; UCEL providers remain an independent operational plane and MUST NOT be consulted by generation-time discovery.**

10. **Rejected alternatives:**
    - *Build 3D/GitHub discovery atop the UCEL COMPONENT-provider framework* — rejected: generation-time consumption is wired through `ComponentDiscoveryEngine`→CSF; a UCEL-based path would be a parallel architecture by construction, and its shadcn/react_bits adapters use direct HTTP/scraping that bypasses connector credential/transport infrastructure.
    - *Extend the UCEL `GitHubComponentProvider` REST client for repo intelligence* — rejected: duplicates `github_mcp`, forfeits fail-closed credential handling and transport hardening from Phases 26–44.2.
    - *A dedicated 3D component framework/model* — rejected: audit found no requirement outside `ComponentPackage` + metadata vocabulary; ADR-0064 already governs the renderer side.
    - *Per-domain ranking engines (3D-specific scoring)* — rejected: violates centralization; extend pipeline profiles instead.
    - *New persistence models for indexed components* — rejected: `nexora.component_index.package_data` already serializes `ComponentPackage`.

11. **Migration/compatibility.** Existing `react_bits`/`shadcn` registry rows continue to work; they gain `capabilities` declarations (and optionally expanded capability_maps) via module data updates (`noupdate` semantics respected — upgrades ship corrected defaults without clobbering operator edits). The F-01 reconciliation changes `McpSourceAdapter.capabilities` return semantics; the only in-tree callers are `ProviderManager.get_capable_providers` and the internal `_execute` guard, both updated together. Deprecated-but-alive code (legacy `source_framework/transport/*`, deprecated `github_adapter.py`, Figma remnants, dead throwaway router in `PlanningEngine`) is recorded for a dedicated consolidation unit; removal is not silently bundled into feature work.

12. **Testing/verification strategy.** (a) Unit: capability reconciliation (declared tokens vs tool-name guard); dynamic adapter resolution incl. allowlist rejection; 3D `ComponentPackage` normalization. (b) Regression: existing react_bits/shadcn adapter mappings and ORM tests updated to the post-44.2 router path. (c) Integration: end-to-end federated search proving an MCP-backed source returns candidates through `SearchEngine` (live `github_mcp` on dev where available, ephemeral runtime otherwise). (d) Acceptance: `ComponentDiscoveryEngine` delivers ranked candidates including 3D packages; builder-integration test asserting candidates reach the enrichment input path. CG gates are not part of this phase's scope.

## Consequences

* **Positive**: both expansions land as configuration + bounded adapter work; single discovery/ranking/resolution path preserved; F-01 eliminated so existing (and all future) MCP-backed sources actually participate in discovery; non-MCP adapters become reachable without a second framework; clear CSF↔UCEL boundary ends the "which plane do I extend?" ambiguity.
* **Negative**: `McpSourceAdapter.capabilities` semantic change requires touching every consumer (small, verified); registry rows must now declare capabilities correctly or sources stay invisible (documented, validated by tests); the four-framework fragmentation is narrowed but not eliminated (UCEL untouched by design); dead-code removal deferred to a dedicated unit.
