# Universal Connector Platform: SDK Authoring Guide

> [!IMPORTANT]
> This document is the definitive engineering standard for authoring connectors on the Universal Connector Platform. Every future connector (MCP, GitHub, REST, Figma, Database, etc.) **must** adhere strictly to the contracts and structural patterns defined here.

## 1. Package Structure
Every connector must be entirely self-contained within `services/connector/connectors/<connector_slug>/`. Do not bleed implementation details into the core platform or runtime.

```text
services/connector/connectors/<connector_slug>/
├── __init__.py           # Exports the connector implementation
├── connector.py          # Implements BaseConnector (Lifecycle & SDK wiring)
├── provider.py           # Implements BaseCapabilityProvider
├── transport.py          # Implements BaseTransport (Execution & IO)
├── authentication.py     # Satisfies auth contracts (even if "None")
├── configuration.py      # Configuration schema & defaults
├── health.py             # Pre-flight and periodic health checks
├── manifest.py           # Returns the canonical ConnectorManifest
└── capabilities.py       # Isolated capability logic modules
```

## 2. Manifest-Driven Registration
Connectors must not dynamically mutate registry state. The platform determines what a connector can do strictly by consuming its `ConnectorManifest` (usually exported from `manifest.py`).

**Requirements:**
- A unique `connector_id` (e.g., `core.local_cli`).
- Accurate `connector_type_id`.
- A fully defined list of `capabilities` indicating what namespaces are provided.
- An accurate `configuration_schema` defined as a JSON Schema dict.
- Declared dependencies and credentials.

## 3. The Lifecycle Contract (`BaseConnector`)
The `BaseConnector` acts as the root interface between the connector and the Runtime.

- **`initialize(context)`**: Fired when transitioning from `CONFIGURED` to `RUNNING`. Establish persistent connections here. Return quickly or spawn async tasks if necessary.
- **`shutdown(context)`**: Fired when transitioning to `DISABLED` or during platform shutdown. You **must** release all resources, terminate child processes, close HTTP sessions, and cancel ongoing tasks.
- **`check_health(context)`**: Must perform a lightweight check ensuring the connector remains viable.

## 4. The Transport Contract (`BaseTransport`)
Transports isolate the "how" from the "what".

- **Responsibilities**: Subprocess spawning, network IO, gRPC stub generation, handling timeouts, buffering stdout/stderr, handling network cancellation.
- **Prohibitions**: Transports must not know about specific capabilities. They send generic payloads and return generic responses.

## 5. The Provider & Capability Contract (`BaseCapabilityProvider`)
- **`execute_capability(namespace, parameters, context)`**: Receives a fully validated request. It routes to specific functions (usually in `capabilities.py`) which then delegate to the Transport.
- Capability modules must remain pure and stateless where possible.

## 6. Authentication & Configuration
- **Authentication**: Even if a connector requires no authentication, it must implement an explicit authentication layer (e.g., returning early or verifying an empty token) to satisfy the SDK contract seamlessly.
- **Configuration**: Hardcoded variables are forbidden. Rely on `context.configuration_snapshot` generated by the runtime using the schema provided in the Manifest. 

## 7. Error Handling & Retry Semantics
- Never crash the `ConnectorEventBus` or Runtime loop.
- Uncaught exceptions thrown during `execute()` are caught by the `ConnectorDispatcher`, which wraps them in a `ConnectorExecutionResult.fail()`.
- Connectors should gracefully raise `ConnectorExecutionError` or context-specific exceptions to trigger early failures where appropriate.
- Retry logic is generally handled at the pipeline layer. The connector itself should fail fast unless dealing with expected transient network jitter inside the transport.

## 8. Testing & Validation Requirements
Every connector must be accompanied by:
- A unit test asserting the manifest is syntactically valid.
- An Architecture Acceptance Test (AAT) verifying lifecycle registration, startup, basic execution, cancellation, and shutdown.
- Tests proving resource cleanup upon shutdown.

## 9. Security Expectations
- Capability implementations must aggressively sanitize `parameters` against path traversal, shell injection, or unauthorized API access.
- Secrets must only be accessed via `context.resolved_credentials`. Do not read `.env` directly within the connector.
