# Connector Architecture Decision Matrix

This document is the permanent architectural reference for the Universal Connector Platform. It tracks every major architectural decision, the alternatives considered, the selected path, the reasoning, and the associated trade-offs.

| Decision | Alternatives Considered | Selected | Reason | Trade-offs |
| :--- | :--- | :--- | :--- | :--- |
| **Source vs Marketplace architecture** | 1. Hardcoded Marketplace<br>2. Generic Source / Catalog abstraction | **Generic Source / Catalog abstraction** | Allows connectors to be sourced uniformly from GitHub, local bundles, enterprise, or marketplaces without coupling to a specific distribution method. | Slightly more complex entity model; requires a sync mechanism across multiple sources. |
| **Manifest / Release / Installation hierarchy** | 1. Flat `ConnectorVersion`<br>2. `Manifest` -> `Release` -> `Installation` | **`Manifest` -> `Release` -> `Installation`** | Distinguishes between published immutable artifacts and mutable deployed instances. | Increased Odoo model count and relationship complexity. |
| **Connector Environment** | 1. Implicit Local Env<br>2. Explicit `ConnectorEnvironment` | **Explicit `ConnectorEnvironment`** | Supports multiple installations of the same connector across different deployment targets (Docker, VPS, CI/CD, etc) without ambiguity. | Environment resolution adds overhead to execution dispatch. |
| **Capability Definition model** | 1. Connector owns capabilities<br>2. Independent `CapabilityDefinition` and `Implementation` | **Independent `CapabilityDefinition` and `Implementation`** | Allows multiple connectors to implement the same canonical capability (e.g., `search.web`), enabling fallback and priority routing. | Connectors must strictly map their outputs to the canonical schema. |
| **Event Bus** | 1. Direct callbacks<br>2. Typed `ConnectorEventBus` | **Typed `ConnectorEventBus`** | Decouples `LifecycleManager`, `HealthMonitor`, and `ConnectorRuntime`, establishing a reactive state architecture. | Tracing event flow requires examining subscriptions rather than call graphs. |
| **Ports & Adapters** | 1. Runtime uses Odoo ORM<br>2. `ConnectorPersistencePort` | **`ConnectorPersistencePort`** | Ensures the `ConnectorRuntime` has zero dependencies on `odoo`, enabling independent testing and platform separation. | Requires writing and maintaining `OdooConnectorPersistenceAdapter` translation layers. |
| **Persistence abstraction** | 1. Memory only<br>2. Database sync via Ports | **Database sync via Ports** | Provides durability across restarts while keeping the core registry fast (in-memory caching) and decoupled. | Synchronization delays; potential split-brain between memory and DB if not handled safely. |
| **Factory architecture** | 1. Runtime instantiates connectors<br>2. External `ConnectorFactory` | **External `ConnectorFactory`** | Strictly isolates dependency injection, provider selection, and transport wiring from orchestration concerns. | Introduces another layer of indirection (`TransportFactory`, `ProviderFactory`). |
| **SDK architecture** | 1. Ad-hoc provider wrappers<br>2. Formal `BaseConnector` SDK | **Formal `BaseConnector` SDK** | Enforces a strict contract (`BaseCapabilityProvider`, `BaseTransport`, etc) for all future connectors, ensuring uniformity. | Connector authors must conform to Nexora SDK rather than using raw third-party SDKs directly. |
| **Runtime ownership** | 1. Embedded in Generation Platform<br>2. Independent sub-system | **Independent sub-system** | The Connector Platform exclusively owns connector discovery, lifecycle, health, and credentials, separate from Generation pipelines. | Requires crossing `ConnectorExecutionTarget` boundary (EP-004) to bridge the two platforms. |
| **Registry architecture** | 1. Odoo-backed queries<br>2. In-memory `ConnectorRegistry` + `CapabilityIndex` | **In-memory + CapabilityIndex** | Ultra-fast `O(1)` capability resolution without blocking database calls during high-throughput execution. | Requires rebuilding index on registry changes or health degradations. |
| **Telemetry model** | 1. Simple enum (`HEALTHY` / `FAILED`)<br>2. Structured `ConnectorHealth` aggregate | **Structured `ConnectorHealth` aggregate** | Enables tracking of drift, latency, rate-limits, and quota exhaustion, critical for multi-tenant SaaS. | Health probes require more sophisticated parsing of provider responses. |
| **Configuration model** | 1. Key/Value JSON<br>2. Document Model (Schema, Defaults, Overrides, Secrets) | **Document Model** | Allows secure injection of secrets (`secret_provider_reference`), environment variables, and validation against a schema. | Configuration resolution is heavier; requires merging multiple dictionaries at runtime. |
